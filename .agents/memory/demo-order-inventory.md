name: Demo order inventory
description: Why DriveGuard's simulated orders do not consume physical stock.
---

Demo orders are a demonstration of the checkout flow, not real sales. Keep their order records and totals separate from physical inventory changes; an administrator adjusts actual stock deliberately.

**Why:** Card checkout is simulation-only, with no payment or fulfillment. Decrementing real stock after a simulated checkout would make the public availability misleading for actual customers.

**How to apply:** Do not claim DriveGuard inventory was reserved; use neutral order confirmation wording without stock-change notices. If real payment and fulfillment are introduced later, revisit this rule and atomically reserve or decrement stock as part of the real order transaction.

The owner describes these as synthetic rather than real cards, but points to the existing website as the required field format and rejected a request for a separate format example. Do not impose a new prefixed identifier format or keep asking for that same sample. They are not generated by the storefront or necessarily drawn from a hard-coded card list. The administrator wants exact issued values visible live to compare the team's entries with what was supplied, without replacing those values with DEMO-prefixed identifiers. This is an admin-controlled internal test mode; when off, typed values remain browser-local.

**Why:** The owner repeatedly explained the external generation and manual comparison requirement. The external server has no API. They explicitly reject an external-server connection or automatic verification: the administrator compares entries with already-issued details manually. Do not describe automatic matching as an owner-requested feature. The earlier DEMO-prefixed substitute did not meet that testing need; do not ask again whether values are generated outside the site.

**How to apply:** Keep the on/off boundary enforced on the server. Inspect the existing field format instead of asking the owner to describe it again. Non-financial test codes can be shown exactly without adding an issuer integration or generation controls; reject actual payment-card credentials rather than accepting them under a test label. For card-formatted values, exact-value display requires verification against issued synthetic records, not acceptance of arbitrary full payment-card numbers or CVC. The owner plans to integrate Stripe before making the sites public; do not treat that future plan as permission to enable unrestricted card capture now or as a request to connect Stripe immediately. Follow the UI-wording rule below; do not reintroduce shopper-facing warnings.

**Why:** The user wants a polished, Stripe-like experience while explicitly keeping the checkout simulated. Provider branding or real-payment security claims would misrepresent what the form does.

**How to apply:** Do not claim a real charge happened. Only introduce payment-provider claims after a real integration is implemented and verified. Use neutral order/verification wording rather than no-charge notices.

**How to apply:** Preserve manual card entry and the existing checkout flow; do not replace the removed button with another autofill or card-generation control.
